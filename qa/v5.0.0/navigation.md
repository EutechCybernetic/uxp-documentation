# Navigation System Architecture

The v5 navigation system operates on a dual-layer hierarchy: **Master Links** and **Navigation Profiles**. Navigation is now its own item under **Administration > Navigation**, with **Profiles** and **Master Links** as top-nav links (no longer tabs under Branding; the old `/branding/navigation` URL redirects). Existing accounts pick up the moved links on the next navigation sync. **Custom Routes** has moved the same way: it is now a top-nav link under **Navigation** rather than under Branding (the old `/branding/routes` URL redirects), existing accounts pick it up on the next navigation sync, and a profile that listed it must add it again.

## Master Links (The Source of Truth)

- **Initialization:** For fresh accounts, the system initially loads default links from application YML files. **Testing focus:** on an account that has never synced, the sidebar shows the full default navigation and every app page opens by its URL; run "Sync from YMLs" and confirm Master Links shows the same tree and the sidebar is unchanged.
- **Sync Logic:** System admins must sync YML data to the database to enable customization. **The sync now asks what to do with edited links (NEW):** if any YML link has been edited in the UI, "Sync from YMLs" first offers *Skip (preserve my changes)* or *Override with YML values* — the prompt used to be missed whenever the edited link was nested under a section, which is nearly always, so edited links were silently kept without saying so. Custom links are never touched either way, the current order is kept unless you untick "Preserve current ordering", and the result now reports the server's counts ("Sync complete: N added, N updated, N deleted.") plus a toast that stays on screen naming how many edited links kept their values. **Testing focus:** edit a link two or three levels deep, then sync — the prompt must appear with the right count, the sidebar "Revert modified links" row must show it too, and after choosing Skip the link must still hold your edit. Then sync again choosing *Override with YML values* and confirm the YML value is back and the Modified chip is gone. For ordering, drag a YML link to a new position and sync twice: with "Preserve current ordering" ticked the position is kept, unticked the YML order returns. A custom link must survive every one of these syncs.
- **Customization:** Full overrides are supported, except on protected and locked links (see Protected and Locked Links below).
- **Custom Links:** **+** on a node adds a child, the root **+** adds a top-level link. A link created in the UI shows the **Custom** chip and is never changed or deleted by a sync. **Testing focus:** add a custom link at the top level and one under an app section, run both sync choices, and confirm both links are untouched.
- **Revert Modified Links:** A YML link edited in the UI shows a **Modified** chip and a revert icon; reverting it restores its YML values. The sidebar "Revert modified links" row shows the count and reverts them all after a typed confirmation. **Testing focus:** edit two YML links, revert one from its node (only that one returns to YML values), then use "Revert modified links" for the other (the row disappears once nothing is modified).
- **Delete a Link:** Deleting a link removes it and all its descendants. **Testing focus:** delete a custom section that has children and confirm the children are gone from Master Links, the sidebar and every profile that listed them.
- **Link Types:** The link form offers View, Dashboard, Sub Dashboard (dashboard Links tab), External Link, Symlink, Redirect, Embedded Dashboard, Group / Label and Dynamic. A View opens its page at its own path; a Dashboard opens `/dashboard/<id>`; an External Link opens the full URL; a Symlink shows its target route's page at the symlink's own URL; a Redirect navigates to its target; an Embedded Dashboard renders a dashboard canvas of its own at a `/view/...` path, configured in place; a Group / Label has no page and opens its first child the user can see; a Dynamic link calls a service or model action whose returned links appear as a group. **Testing focus:** create one custom link of each type, click each in the sidebar and open each URL directly; the address bar and page must match the type (the symlink keeps its own URL, the redirect ends on the target URL).
- **Sidebar and Header Levels:** Levels 1 to 3 of the tree form the sidebar; levels 4 and 5 move to the header row and carry a **Top Nav** chip in the tree editor (profiles split the same way). On a dashboard, the header shows the dashboard's own links instead. **Testing focus:** build a custom branch five levels deep, confirm levels 4 and 5 show the Top Nav chip and appear in the header when a level-3 page is open, then open a dashboard that has links and confirm the header shows those links.
- **Public Links:** "Allow public access (no login required)" on a link shows a **Public** chip, and its URL opens for a visitor without a session. Public is not inherited: children of a public link still need a login. A locked link can never be made public. **Testing focus:** make a custom view link public, log out and open its URL (the page loads); open the URL of a non-public child under it (login page); confirm the public option is not offered on an Administration link.
- **Editing Keeps Your Place (NEW):** A tree no longer resets itself while it reloads. Once it has content it stays on screen during a reload — dimmed, with a small spinner — instead of being replaced by the loading skeleton, so the scroll position holds and expanded sections stay open; the skeleton is now only for the very first load. Expansion also survives data that comes back marked collapsed-by-default, survives a section that momentarily reloads with no children, and two reloads in quick succession can no longer let the slower one overwrite the newer tree. This holds for every tree in the product — Master Links, profiles, Compare vs Master, the Page Editor's view trees. **One caveat:** a section whose children are fetched on demand keeps the children it has already loaded across a reload — collapse and expand it to pull them again (no tree in the product loads its children that way today, so nothing here is affected). **Testing focus:** expand a few sections deep in Master Links, scroll to the bottom, then cause a reload (save an edit, run a sync) — nothing collapses, the scroll does not jump, and the tree dims briefly instead of flashing a skeleton.
- **Visibility:** Restrict links using User Groups and App Roles. A link passes when it has no restrictions, lists the user's group, or lists any app role the user holds. **Testing focus:** create a user group A, a user role B, and three test users (one in A, one holding B, one with neither); restrict one custom view link with a page to group A and another to role B, then log in as each user: each sees only the link they match, and the other link's URL gives Access Denied.
- **App Placeholders:** A master link can be saved with "Fill children from app" — that app's links from its Configuration.yml materialise as children immediately and refresh on each YML sync. The node shows a "Fills from \<app\>" chip. Only apps without a default menu location are listed. **Testing focus:** add a custom section, pick an app from "Fill children from app", save, and confirm the app's links appear under it with the chip; run "Sync from YMLs" and confirm they are still there (not duplicated).
- **New Apps:** An enabled app with no links in Master Links shows as a "New app" row in the sidebar. A **Default location** chip means the app has a place in the default navigation and "Sync app navigations" restores it there; an **Orphan** chip means it has none, so place it with "Fill children from app". **Testing focus:** delete every link of one non-protected app from Master Links, confirm the New app row appears with the right chip, and restore the app with a sync.
- **Compare and Sync One App:** "Sync app navigations" opens a comparison for one selected app: its YML links on one side, the current navigation on the other, with New and Modified links marked. Selected changes (or Merge new, Merge modified, Merge all) are applied with a typed confirmation. A YML link whose path a custom link already uses is not applied and the message names it. **Testing focus:** edit one of an app's YML links and delete another, open the comparison for that app, confirm one shows as Modified and the other as New, merge only the new one and confirm the edit is kept, then merge the modified one and confirm the YML value returns.
- **Link Path Validation:** Internal links must start with `/view/`; a Sub Dashboard link (dashboard form) must start with `/dashboard/` and is composed as `/dashboard/<dashboard id>/<section>`; symlink/redirect targets may use either. Absolute URLs are rejected for internal types; unsafe characters `( ) [ ] { } + ! * ?` and a bare `:` are rejected. The External Link type accepts full URLs but blocks `javascript:`-style schemes. **Query strings have their own field now (NEW):** the Link box stays a path and still refuses `?`, and parameters go in the separate **Query parameters** field (`key=value&key2=value2`), offered on View, Dashboard, Sub Dashboard, Symlink (on the *vanity* URL — the target stays a plain path) and Redirect (on the *target*). Keys the shell itself uses are refused there — `embedded`, `__embed__`, `configurepage`, `configuredashboard`, `pe_node`, `pe_mode`, `pe_tab`, `next`, `preview` — as are values containing `?`, `#` or spaces. A **custom route** is a path and refuses `?` outright (the message points you at the link's Query parameters field instead). The same form is shared by Master Links and the dashboard Links tab, so test both. **Testing focus:** on a View link try `/my-page` (no `/view/`), `https://example.com/page`, `/view/my(page)`, `/view/my-page?x=1` and `/view/item/:` and confirm each is refused with its message; on an External Link try a `javascript:` URL (refused) and a normal `https://` URL (saves); in Query parameters try `embedded=1`, `a=b c` and `a` (all refused) and `a=1&b=2` (saves).
- **Links With Parameters (NEW):** A link can open a page with defaults. Point a link at `/view/digital-twin` and set Query parameters to `objectKey=<location key>&objectType=Location`, and clicking it lands on `/view/digital-twin?objectKey=<location key>&objectType=Location` — the Digital Twin page opens on that building instead of the site view. Any page that reads query parameters works the same way; the Digital Twin page is only the example. The parameters reach the page as props exactly as if they had been typed into the address bar (a parameter in the URL still wins over a prop configured on the page). Routing is unaffected: the **route is the path**, so the page, its permissions and Configure Page all behave as they do on the plain URL. The sidebar highlights the link whose parameters match the current URL — with both a plain `/view/digital-twin` link and a `?objectKey=<location key>` one in the menu, only the matching one lights up, and the plain one lights up on the bare URL. **Known limitation:** two links on one path share a single route, so they should differ only in label, icon and parameters — give them different pages or permissions and the **last** of them in tree order decides for both, silently: the server collapses them into one route key before the shell ever sees them, so nothing warns you. Configure Page has the mirror-image catch — it edits the **first** link on that path, which may not be the one whose page is being served. **Sync:** adding parameters to a link that came from YML marks it Modified, so a normal "Sync from YMLs" keeps them (choose *Skip*) and an override sync puts the YML link back. **Testing focus:** add parameters (for example the key of a location you created) to a YML link whose page reads them, confirm the Modified chip, the URL, the page contents and the highlight; add a second link on the same path with different parameters and check each highlights only on its own URL; then sync both ways.
- **Dashboard Picker:** Pages and searches server-side — verify it stays responsive on accounts with thousands of dashboards.
- **Restricted Sections Gate Their Pages (NEW):** A section's User Groups / App Roles now apply to everything under it by URL as well as in the sidebar — every level must pass. A user who holds a role granted on a page but not the role its parent section requires gets a full-page Access Denied at that URL; before, the page opened (or the shell denied it after the page shell had drawn). **Testing focus:** restrict a section to role A and a page under it to role B, then visit that page's URL as a user with only B.

## Navigation Profiles

A profile is a curated subset of Master Links arranged in a custom hierarchy.

- **Association Rule:** Each User Group can be linked to at most one profile (one profile can be used by multiple groups). A group with no profile sees the full master navigation. Deleting a profile drops its groups back to master navigation. **Testing focus:** assign group A to profile 1, then assign it to profile 2 (from the UI and with `sdm assignnavprofile`); group A must end up on profile 2 only. Delete profile 2 and confirm a member of A sees the master navigation after a reload.
- **Create, Copy and Delete:** "+ New Profile" takes a label and user groups. Copy creates "\<label\> (Copy)" with the same links and arrangement and lets you pick user groups that are not on another profile. Delete asks for confirmation and removes the profile's link assignments; the master links stay. **Testing focus:** create a profile, arrange a few links, copy it and confirm the copy has the identical tree; delete the original and confirm the copy and Master Links are unchanged.
- **Hierarchy:** Profiles simply refer to Master Links (no data duplication). They can, however, have a unique parent-child structure. **Testing focus:** in a profile, drag a link under a different parent and reorder a section; confirm a member of the profile's group sees the new arrangement after a reload and that Master Links is unchanged.
- **Adding and Removing Links:** "Compare vs Master" (or "Compare & Add from Master" on an empty profile) shows master links next to the profile; links already in the profile carry an **In Profile** chip. Add a single link or a whole subtree, or use Copy All. Removing a link removes it and its profile children from this profile only; "Remove all links" empties the profile without deleting it. **Testing focus:** add a subtree and a single link, confirm they land under their master parent when that parent is in the profile; add a new master link afterwards and confirm Compare vs Master offers it (profiles never pick up new master links automatically); remove a link and confirm Master Links and other profiles still have it.
- **Modification Behavior:**
  - Editing a link from a profile (label, icon, page, destination) changes the **master link**, so the change shows in every profile that uses it.
  - **Access is edited in Master Links only (NEW):** public access, user groups and app roles are not profile settings. The link form opened from a profile no longer offers those fields — it shows the link's current access read-only, with a note pointing to Master Links. **Testing focus:** open a link with app roles from a profile (tree editor and Compare vs Master), change the label, save, and confirm in Master Links that the roles are unchanged.
  - Deleting a link from a profile *removes the reference* but does not delete the Master Link.
- **Deleted Links Leave Profiles (NEW):** Deleting a master link also removes it from every profile. A YML link deleted in Master Links and brought back by a later sync is *not* re-added to profiles automatically — add it again. **Delete all now removes protected links as well (NEW):** it empties the master list completely, and until the next sync the sidebar and routes come straight from the YML files — the full default navigation, not just the Administration tree. `sdm resetnavigation` (wipe and re-sync) keeps profile membership, and profile edits, new master links and custom-route changes now take effect without Clear cache. "Delete all links" asks you to type `delete`, and is refused while any profile exists (the message points you to "Sync from YMLs"). **Testing focus:** add a YML link to a profile, delete it in Master Links (gone from the profile), sync (back in Master Links, still not in the profile). With a profile present, try "Delete all links" and confirm the refusal; with no profiles, delete all and confirm Master Links is empty while the sidebar shows the full default navigation, then sync to restore it.
- **No Logout Banner:** Creating, assigning or deleting profiles refreshes navigation for the affected groups without triggering the forced-logout countdown banner. **Testing focus:** keep a session open as a member of a group, assign that group to a profile from another session, then reload: the sidebar follows the profile and no countdown banner appears.

## Route Errors

- **Restricted Route:** Navigating to a URL the user's roles exclude shows an "Access denied" page (not a 404).
- **Unknown Route:** A typo'd/unknown URL shows a 404 page.
- **Anonymous:** An anonymous user hitting a non-public route is redirected to the login page, and returns to that URL after logging in. **Testing focus:** as a restricted user open a URL your roles exclude (Access Denied) and a made-up `/view/...` URL (404); log out, open a non-public page URL, log in, and confirm you land on that page.
- **Default Pages:** `/view` redirects to the welcome page and `/view/system/home` to the user group's home page. **Testing focus:** set a different home page on two user groups and open `/view/system/home` as a member of each.
- **Embed Mode:** `?embedded=1` renders a page without the sidebar and header, for iframes. **Testing focus:** open any page with `?embedded=1` directly and inside an iframe; only the page content shows.
- **Dashboards:** Dashboard URLs are not routes; access is checked when the dashboard is opened. See Dashboard Access in [Widgets & Dashboards](widgets-dashboards.md).
- **Bad Links:** One invalid navigation link no longer breaks the whole app — only that link fails (a browser console warning names it); everything else keeps navigating.
- **One Error Component:** All error pages and notices now render through one shared component. The 404 and Access Denied pages look as before; gated detail tabs and widgets show a compact inline notice instead of a full page; a page or widget whose component can't be found shows a centred "Unable to find the view" block.
- **Loading Before Error (NEW):** A page never shows "Unable to find the view" while it is still loading. Pages show a skeleton (toolbar + rows), detail tabs and widget tiles show a spinner, until the component resolves. If the component's bundle is known but has not registered the component yet (app bundles load in the background), the loading state is held for up to **15 seconds** before the error appears; the moment the component registers, the view renders. A component whose bundle is unknown, or whose script fails to load, shows the error immediately. **Testing focus:** cold-load any app page, and switch between apps after clicking around — no error flash at any point.
- **Hidden Empty Groups (NEW):** A sidebar group whose children the user cannot see is hidden for that user (its URL gives Access Denied), and clicking a group lands on the first child the user can see (it used to land on Access Denied when the first child was restricted); in-app links are preferred over external ones. Users who can see the children see the group as before. **Testing focus:** restrict all children of a group, then only its first child, to a role the test user lacks.
- **Profiles Only Arrange (NEW):** A profile decides what the sidebar shows and in what order — never what a user may open. A profile user can still reach by URL any master link their permissions allow, including links the profile leaves out; and a link the profile moved elsewhere keeps the permissions of its place in the master tree, not of its new parent. Configured page props set on a master link reach profile users too. A sidebar group the profile leaves out keeps its URL as Access Denied rather than a 404. **Testing focus:** as a profile user, open the URL of a master link that is not in the profile (it works), one under a master section your roles exclude (Access Denied), and a group URL the profile omits (Access Denied).
- **Custom Links Without a Page (NEW):** A non-public custom view link saved without a page no longer registers a route of its own, so it cannot break the page at that URL or drop that page's role gate. The URL works if an app or a custom route serves it (with that route's roles); otherwise it is a 404. Public page-less links behave as before (they still make the URL public). **Testing focus:** create a custom route on a new path restricted to role A, then add a non-public custom View link to that path with no page: a user with role A opens the route's page, a user without it gets Access Denied; change the link's path to one nothing serves and confirm clicking it gives a 404.
- **Pages You Cannot Render Are Hidden (NEW):** A page component's `bundle.json` roles are now applied by the server as well as by the page itself. A link to a page whose roles the user lacks disappears from the sidebar — and a section left with nothing visible disappears with it — while that page's URL gives a full-page Access Denied instead of the in-shell notice. This holds wherever the page is reached: app links, `otherRoutes` detail pages and custom routes alike, and it cannot be overridden from the UI (unlike a link's or a route's own permissions). A page whose component the server does not know about is not gated. Uploading or removing a bundle takes effect on the next page load, without Clear cache. **Testing focus:** as a user without `System:canmanage` / `System:canmanageuserroles`, confirm Administration and its Admin Tools section are gone from the sidebar and their URLs give Access Denied; add a custom route pointing at a page gated by a role you lack and confirm that URL is Access Denied too. As an admin, confirm the section and every page under it are unchanged.
- **No Flash Before Redirects (NEW):** Following a redirect — a group, or `/view` — no longer flashes "Unable to find the view" before the target page, including in embed mode (`?embedded=1`). Known, unchanged: the redirect drops `?embedded=1`, so the target renders with the full shell.
- **Admin Diagnostics:** On "Unable to find the view", users with the `System:cancustomisepagesanddashboards` role also see the cause (no component configured / bundle not delivered / bundle loaded but component not registered / bundle failed to load), the component id, what the bundle actually registered, what to check, and a **Manage Bundles** button for uploaded widget bundles. Everyone else sees only the friendly message.
- **Server Check (NEW):** For the "bundle not delivered" cause the block first shows "Checking with the server..." and then names what the server knows about the id: an uploaded widget bundle this page was loaded without (reload / clear the modules cache), an app component whose app scripts were not delivered, a marketplace component not installed for this account, or a component the server does not know at all. If the check itself fails, the generic wording stays. Test with a widget bundle uploaded in another tab (reload fixes it) and with a made-up component id (unknown to the server).
- **Fits Its Container:** These notices size themselves to where they are — a block placed in a small widget tile becomes an inline row, then just an icon (click it for the detail). Nothing should ever be clipped or scroll.
- **Dead-End Sections Are Hidden (NEW):** A sidebar section without a page of its own (an app root, say) is served by whatever route owns its URL — usually a redirect into its first page. When that redirect leads only to pages the user is not allowed to open, the section can only end in Access Denied, so it is now hidden: it stays as a group if any of its children are still visible (clicking it opens the first of those), and disappears entirely if none are. Either way the section's own URL now answers Access Denied itself instead of following the dead redirect. A symlink whose target the user may not open is hidden too. Only a certain denial hides an entry: a section or symlink whose target simply does not exist is left as before (clicking it still gives the old Not Found), and so are entries whose target the user can open, links with a page of their own, symlinks to a dashboard (a dashboard is checked when it is opened), and redirect, external and dashboard links. **Testing focus:** create a user whose roles grant access to only one installed app, and confirm the root sections of every other app are gone from the sidebar and their URLs give Access Denied. Under a section that user can see, add a symlink whose target route is restricted to a role the user lacks: the symlink disappears from their sidebar. Add a symlink to a target path that does not exist: it stays, and clicking it gives Not Found. As an admin, confirm every section and symlink is present and lands where it always did.
- **Bundle Load Failure:** A widget whose script bundle fails to download shows the error block instead of spinning forever.
- **Protected and Locked Links (NEW):** Links the YML marks as system-managed now say so and stay that way. The whole **Administration** menu is Protected and Locked: its nodes show those chips, have no edit, delete or **Configure Page/Dashboard** button, have **no drag handle at all**, refuse to be dragged, reordered or moved under another parent, refuse any change to their user groups, app roles or public flag, and the Page Editor refuses to repoint or reset their page — each with a message saying why. You can still **add a child** under a protected section, and that child is an ordinary custom link: editable, deletable, and it may be public — but it always sits **after** the system links. Dragging it above one of them shows no drop indicator and is refused with "Custom links stay after the system links in a protected section"; a new child added without a position lands at the bottom. Everything outside the protected subtree (Digital Twin, custom links, other apps) behaves exactly as before, including reordering the top-level sections even though Administration sits among them, and dragging a custom or app link above or below Administration (only Administration itself has no drag handle). The one write that still reaches a protected link is a YML sync — full sync, per-app sync from the comparison view, or Revert — and those now work on locked links too, where the lock used to block them silently. **Testing focus:** try every edit, move, delete and access change on an Administration link and confirm each is refused with a message; add a child under it and confirm it appears at the bottom and cannot be dragged above a system link; edit and delete that child; reorder the root sections; then run a per-app sync for System and confirm it applies.
- **Protection Now Covers a Whole App (NEW):** The flags are set once, on the section that slots an app (or at the app's own root), and everything the app contributes inherits them — its navigation links **and** the routes it defines in YML that never appear in the menu. In practice every `/view/admin/...` URL of the System app is now system-managed. A single link or route can still opt out in YML. **Testing focus:** confirm the Administration pages still open normally for an admin and are still denied for a restricted user — the inheritance changes who may *edit* the navigation, never who may *open* a page.
- **The Page Configurator Steps Aside (NEW):** On a system-managed page the floating "Edit page" pencil is gone, and opening the page with `?configurepage=1` in the URL shows a compact warning — "This page is system-managed" — with a Back button, instead of the page editor. Nothing of the editor loads: no tabs editor, no widget drawer. **Testing focus:** open an Administration page (e.g. General Settings) and confirm there is no pencil and that adding `?configurepage=1` shows the warning; open a page outside Administration (a custom view link with a page, for example) and confirm the pencil and the editor are still there.

# Custom Routes

Located under **Navigation**, custom routes allow for the definition of links outside the standard navigation (e.g., detail pages like `location/details/<locationkey>`). A custom route takes precedence over a route an app defines in its YML `otherRoutes`. A navigation link with a page or a destination owns its URL; to serve that URL with a custom route, remove the link's page or point the link elsewhere.

- **Create, Edit and Delete:** "Add Route" takes a route path (`:param` segments allowed), label, title, page and access; each row can be opened in a new tab, have its page configured, be edited or deleted; "Delete all routes" removes every custom route after confirmation. **Testing focus:** add a route such as `/my-details/:id` pointing at a page, open it with a value, edit its page and confirm the new page renders, then delete it (404).
- **Access:** Access is granted if the user matches any listed User Group or any App Role; with both empty, every logged-in user may open it. The page's `bundle.json` roles apply on top. **Testing focus:** restrict a route to group A and check it as a member of A (opens), a user holding neither (Access Denied) and a logged-out visitor (login page).
- **Override an Existing Route:** The "Override an existing route" picker lists routes the apps define in YML `otherRoutes`; a custom route on that path replaces it. **Testing focus:** override an app detail route with a different page and confirm the custom page renders at that URL; delete the custom route and confirm the app's page is back. Then add a navigation link with a page on a path a custom route serves: the link's page wins until its page is removed.
- **Paths Only:** A route path refuses `?` and points you to the link's Query parameters field. **Testing focus:** save a route path containing `?x=1` and confirm the message.

**Protected URLs are refused (NEW).** A URL that belongs to a protected or locked navigation link, or to a YML route marked `protected` / `lockAccess`, cannot be served by a custom route: saving one on that path is refused with "This URL is protected and cannot be served by a custom route", and such routes no longer appear in the "Override an existing route" picker. Because a protected section now covers the whole app it slots, this is **every** `/admin/...` route of the System app, including the ones that only redirect. The same applies to a custom navigation link pointing at a protected URL. **Testing focus:** try to create a custom route on an Administration page's path (e.g. `/admin/general-settings/general` or `/admin/general-settings/lucy-api`) and confirm it is refused; confirm the picker offers no `/admin/...` route; confirm a normal path (a Digital Twin route, say) still saves and still overrides.

# Command Line (sdm)

The same operations an admin runs from **Administration > Navigation**, for setup scripts, automation and recovery. Every command takes the account name (for example `sdm myaccount listnavprofiles`); commands that change navigation or a profile clear the cached navigation on all servers, so no restart or Clear cache is needed.

- **syncnavigation:** `sdm <account> syncnavigation [--force] [--reset-order]` runs the same sync as "Sync from YMLs": new links added, existing ones updated, links removed from YML deleted and dropped from profiles, custom links untouched. By default edited links keep their values and the manual order is kept; `--force` overwrites edited links, `--reset-order` restores the YML order. It reports added, updated, deleted and skipped counts. **Testing focus:** edit one YML link and move another, run with no flags (skipped count 1, edit and position kept), with `--force` (edit gone), then with `--reset-order` (YML order back); a custom link survives all three.
- **resetnavigation:** `sdm <account> resetnavigation` deletes all master links and runs a forced sync with the YML order, protected links included. Custom links are gone; profiles keep their user groups and every link that still exists. **Testing focus:** add a custom link, edit a YML link and put both in a profile, then run it: the custom link is gone from Master Links and the profile, the edit is reverted, and the profile keeps its groups and its other links.
- **createnavprofile:** `sdm <account> createnavprofile "<name>" <group1[,group2,...]>` creates a profile holding every master link in the master arrangement and assigns the groups (by user group id). A group already on another profile moves to the new one; an unknown group is skipped. The name must be new and master links must exist. It reports the link count and the assigned, moved and skipped groups. **Testing focus:** run it with one free group, one group already on another profile and one made-up id, and check the report and the Profiles page; run it again with the same name (error, no duplicate); on an account that has never synced (error asking for a sync first).
- **assignnavprofile:** `sdm <account> assignnavprofile "<name>" <group1[,group2,...]>` adds groups to an existing profile with the same moved and skipped reporting; groups already on it stay. **Testing focus:** assign a free group and a group from another profile (moved), then use a profile name that does not exist (error).
- **listnavprofiles:** `sdm <account> listnavprofiles` lists every profile with its key, name, link count and user groups. **Testing focus:** compare the output with the Profiles page after each command above.
- **copyalllinkstoprofile:** `sdm <account> copyalllinkstoprofile <profileKey>` replaces a profile's links with every master link in the master arrangement, for a profile that lost links. The key comes from `listnavprofiles`. **Testing focus:** remove all links from a profile in the UI, run it with that profile's key, and confirm the profile tree matches Master Links and its user groups are unchanged.
- **resetv5cache:** `sdm resetv5cache [<account>|all] [all|appconfig|modules|login|localisation]` clears the v5 caches on all servers: navigation and routes, uploaded widget bundles, the login page, or localisation messages. Both arguments default to `all`. Only needed after a change made outside the UI and these commands, such as a deployed `Configuration.yml`. **Testing focus:** run each scope for one account and for `all`, and confirm pages, navigation, the login page and translations still load correctly afterwards.
